The Python RAG Service exposes search and grounded answer generation as two public endpoints.
`POST /v1/search` returns search results from the hybrid retrieval pipeline.
`POST /v1/answer` uses that same pipeline, then generates an answer from the retrieved evidence.

Both endpoints use the same hybrid retrieval pipeline, which combines vector and lexical retrieval,
reranks the candidates, and applies the support gate. A request starts with a query, and the retrieval
pipeline selects chunks for that query.

Search returns those chunks as search results. The answer endpoint assembles the chunks into context, and the
model generates an answer from that context. The application validates the proposed citations before the endpoint
returns the answer and its sources.

```text
Search: Query → retrieval → search results
Answer: Query → retrieval → context → answer generation → citation validation → answer and sources
```

Search returns an empty results list when retrieval finds no qualifying results. Answer generation instead reports whether
the available evidence was sufficient through `sufficient_evidence`; when it's `false`, `sources` is empty.

## Key capabilities

### Search

`POST /v1/search` returns the query and a ranked list of search results. You can set `limit` on the request. The default is 5.
Each result includes an `excerpt` containing the retrieved chunk text, along with the document title, heading path, source URL, and rerank score.
You can pass optional metadata filters to narrow which chunks retrieval considers. `POST /v1/answer` accepts the same filters.

The support gate can return no relevant results when the retrieved content doesn't adequately support the query.
`POST /v1/search` then returns an empty `results` list.

See [Search documentation](/docs/search-and-answer/search-documentation) for a closer look at how `POST /v1/search` works.

### Answer generation

`POST /v1/answer` retrieves up to 5 chunks, then generates an answer from that context.
The grounded-answer prompt instructs the model to answer only from the supplied context.
The response includes the answer, the sources cited in it, and `sufficient_evidence`.

Each cited source includes a citation ID and the supporting chunk's text, title, heading path, and URL.
The application validates the model's proposed citations against the retrieved chunks before it returns them.
When `sufficient_evidence` is false, `sources` is empty.

See [Generate grounded answers](/docs/search-and-answer/generate-grounded-answers) for a closer look at how `POST /v1/answer` works.

## Choose an endpoint

Use `POST /v1/search` when your application needs the retrieved documentation.
That includes a search results page, a list of source passages, or any workflow that consumes chunks directly.

Use `POST /v1/answer` when your application needs a written response grounded in that documentation.
The included WordPress client follows this split. Search calls `POST /v1/search`, and Ask calls `POST /v1/answer`.

| You want to | Call |
| --- | --- |
| Show ranked documentation for a query | `POST /v1/search` |
| Choose how many search results to return | `POST /v1/search` |
| Pass retrieved chunks into your own application logic | `POST /v1/search` |
| Return a written answer with sources a reader can open | `POST /v1/answer` |
| See whether the retrieved evidence was sufficient | `POST /v1/answer` |

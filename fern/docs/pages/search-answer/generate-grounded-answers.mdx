`POST /v1/answer` retrieves up to 5 chunks and uses the selected context to generate an answer. The response includes
the answer, its cited sources, and whether the evidence was sufficient.
The endpoint calls an OpenAI language model (LLM). That call needs `OPENAI_API_KEY` in the service's `.env`.

<Markdown src="/docs/snippets/local-service-examples.mdx" />

## Prerequisites

- **[Configure the service](/docs/get-started/configure-the-service)**: Set `OPENAI_API_KEY` in `.env`. `POST /v1/answer` uses that key when it calls the OpenAI LLM.
- **[Index WordPress content](/docs/index-content/index-wordpress-content)**: Build the index that answer generation retrieves.
- **[Authentication](/docs/get-started/authentication)**: Set `RAG_API_KEY` and send that value in the `X-API-Key` header.

## Send an answer request

<Markdown src="/docs/snippets/send-request-header-body.mdx" endpoint="POST /v1/answer" />

The request doesn't include `limit`. Sending `limit` returns `422` with `validation_error`.

<CodeBlocks>

```bash curl
curl -s -X POST http://127.0.0.1:8000/v1/answer \
  -H "Content-Type: application/json" \
  -H "X-API-Key: your-long-random-api-key" \
  -d '{"query": "Why does inconsistent terminology cause retrieval failures?"}' \
  | python3 -m json.tool
```

```python Python
import json
from urllib.request import Request, urlopen

body = json.dumps({
    "query": "Why does inconsistent terminology cause retrieval failures?",
}).encode()

request = Request(
    "http://127.0.0.1:8000/v1/answer",
    data=body,
    headers={
        "Content-Type": "application/json",
        "X-API-Key": "your-long-random-api-key",
    },
    method="POST",
)

with urlopen(request) as response:
    payload = json.loads(response.read().decode())
    print(json.dumps(payload, indent=2))
```

</CodeBlocks>

## Narrow retrieval with filters

Add `filters` when you want retrieval to consider only chunks with matching metadata.
Supported filters are `document_id`, `source`, `source_id`, and `content_type`.
They follow the same rules as `POST /v1/search`. See [Search documentation](/docs/search-and-answer/search-documentation) for how a single value and a list match.

<CodeBlocks>
```bash curl
curl -s -X POST http://127.0.0.1:8000/v1/answer \
  -H "Content-Type: application/json" \
  -H "X-API-Key: your-long-random-api-key" \
  -d '{
    "query": "Why does inconsistent terminology cause retrieval failures?",
    "filters": {
      "content_type": "post"
    }
  }' \
  | python3 -m json.tool
```

```python Python
import json
from urllib.request import Request, urlopen

body = json.dumps({
    "query": "Why does inconsistent terminology cause retrieval failures?",
    "filters": {
        "content_type": "post",
    },
}).encode()

request = Request(
    "http://127.0.0.1:8000/v1/answer",
    data=body,
    headers={
        "Content-Type": "application/json",
        "X-API-Key": "your-long-random-api-key",
    },
    method="POST",
)

with urlopen(request) as response:
    payload = json.loads(response.read().decode())
    print(json.dumps(payload, indent=2))
```

</CodeBlocks>

The service trims `query` and each filter value, then counts Unicode code points. A query can contain
1 to 2,000 characters. A filter value can contain 1 to 256 characters. A filter list can contain 1 to
50 values. An unknown filter name, an empty filter value, a value outside those limits, or an
unexpected field returns `422` with `validation_error`. A body larger than 65,536 bytes (64 KiB)
returns `413` with `request_too_large` before JSON parsing. See [Errors](/reference/errors).

## Use a grounded answer

When `sufficient_evidence` is `true`, show `answer` and connect each citation in that text to `sources`.
A citation is a marker such as `[S1]`. It matches the `citation_id` on one source.
The grounded-answer prompt instructs the model to answer only from the retrieved context and to place each citation after the claim it supports.

The application checks those citations against the retrieved chunks before it returns the response.
`title`, `heading_path`, `excerpt`, `url`, and `anchor` come from the cited chunk.
`sources` lists the chunks the answer cites, in the order those citations first appear. It doesn't list every retrieved chunk.

This sample shows the response shape. Titles, excerpts, and URLs come from your index:

```json
{
  "query": "Why does inconsistent terminology cause retrieval failures?",
  "answer": "Inconsistent terminology can cause retrieval failures because the query and documentation may use different language for the same concept. [S1]",
  "sources": [
    {
      "citation_id": "S1",
      "chunk_id": "wordpress:page:1:chunk:v1:<sha256>",
      "document_id": "wordpress:page:1",
      "title": "Retrieval Failures",
      "heading_path": ["Vocabulary mismatch"],
      "anchor": "vocabulary-mismatch",
      "excerpt": "Inconsistent terminology can make relevant content harder to retrieve.",
      "url": "https://example.test/retrieval-failures"
    }
  ],
  "sufficient_evidence": true
}
```

- <Markdown src="/docs/snippets/real-chunk-id-format.mdx" />
- `anchor` is the heading anchor, and it's `null` when the chunk has no anchor.
- Use `url` with `anchor` when you link a reader to the cited passage.

See [Answer generation and citations](/docs/architecture/answer-generation-and-citations) for how context, generation, and citation checks fit together.
See [Answer API](api:POST/reference/answer) for the response schema.

## Handle insufficient evidence

When the context doesn't contain enough information to answer the query, the generated response
sets `sufficient_evidence` to `false` and `sources` is empty. The prompt instructs the model to say that the
available sources are insufficient. The wording of `answer` can vary. A query the index can't support
can return this shape:

```json
{
  "query": "What is the capital of Mars?",
  "answer": "The available documentation does not provide enough information to answer this question.",
  "sources": [],
  "sufficient_evidence": false
}
```

Show that answer on its own. `sources` is empty, so there are no citations to display.

Your client can show the answer with its sources when `sufficient_evidence` is `true`, or show the answer alone when it's `false`.

### 422 `validation_error`

Check the query length and the supported filters.
`POST /v1/answer` returns `422` with `validation_error` when the request doesn't match the schema.
A query can contain 1 to 2,000 characters after trimming. The route still rejects `limit`.

### 503 `answer_unavailable`

`POST /v1/answer` returns `503` with `answer_unavailable` when it can't finish the answer.

If `GENERATION_ENABLED` is `false`, the service returns this error for an authenticated, valid request.
It doesn't build the answer generator or call Voyage, OpenAI, or Qdrant for that request.
The API log uses `operation=generation` and `reason=generation_disabled`.
Set `GENERATION_ENABLED` to `true`, set `OPENAI_API_KEY`, and restart the API.

When answer generation is on, startup requires a non-empty `OPENAI_API_KEY`.
After startup, a temporary retrieval or language-model failure, context assembly, or citation checking can still produce this error.

`OPENAI_TIMEOUT_SECONDS` bounds each OpenAI attempt. It doesn't set a deadline for the whole answer request.
The default `OPENAI_MAX_RETRIES` is 0, so a timed-out generation call isn't sent again unless you raise that limit.

A missing `OPENAI_API_KEY` at request time returns `500` with `configuration_error` instead.
Restart the API after you change `.env`, then retry the request.

### 500 `configuration_error` and `internal_error`

`POST /v1/answer` returns `500` with `configuration_error` for a known configuration problem found
while handling the request. It returns `500` with `internal_error` for an unexpected programming error.
Each code uses one public message. The log names the operation and the reason.

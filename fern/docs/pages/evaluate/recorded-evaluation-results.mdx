This benchmark records how the Python RAG Service performed on [The Doc Landscape](https://doclandscape.com/) WordPress corpus using dataset
version <code>{evaluationDatasetVersion}</code>. The October 22, 2026 snapshot contains the test cases, retrieved evidence, and generated answers
behind the results. Use them to inspect individual cases and compare your own evaluation runs.

Retrieval passed 21 of 22 cases. All 22 cases passed the answer structural checks. Retrieval and answer evaluation
ran separately on October 22. This snapshot doesn't include qualitative review artifacts; the human-review status
is described below.

## Evaluation dataset

The dataset is <code>{evaluationDatasetId}</code>, version <code>{evaluationDatasetVersion}</code>. It contains 22 cases: 14 expect relevant chunks and
sufficient evidence, and 8 expect no chunks and insufficient evidence. Every case filters retrieval to
`source: wordpress`.

The reports record the following settings.

| Setting | Recorded value |
| --- | --- |
| Corpus | The Doc Landscape WordPress content |
| Qdrant collection | `rag_chunks` |
| Embedding model | `voyage-4-lite` |
| Retrieval support cutoff | `0.70` |
| Requested chunks per query | `5` |
| Generation model for the answer run | `gpt-5.6-terra` |

Retrieval can return fewer than 5 chunks or none. [Evaluation architecture](/docs/architecture/evaluation-architecture)
explains how retrieval, answer evaluation, and human review connect.

Mean precision covers 13 answerable cases. The remaining case, `updated-content-001`, returned an unjudged chunk, so its
precision is `null` and it's excluded from the mean. Read the precision value alongside the number of
precision-evaluable cases.

Every answerable case retrieved at least one primary source. The `multi-section-001` case still failed because
its pass rule requires every primary source. The case examples below show that coverage failure.

## Findings

### A primary hit with incomplete source coverage

The `multi-section-001` case asks:

> How can lost context during chunking, weak source authority, and missing metadata each cause retrieval failures?

The dataset identifies 7 relevant sources, including 3 primary sources. The retrieval run returned 5 relevant
chunks and matched 1 of those primary sources.

| Retrieval result | Value |
| --- | ---: |
| Relevant returned chunks | 5/5 |
| Primary sources retrieved | 1/3 |
| Primary hit | `true` |
| Precision@5 | 1.000 |
| Recall@5 | 0.714 |
| Reciprocal rank | 0.200 |
| Case passed | `false` |

The case failed because two designated primary sources were missing. A primary hit and high precision therefore
coexist with incomplete source coverage.

The October 22 answer for this case passed its structural checks. Retrieval requires all designated primary sources
for a `multi_section` case, while answer evaluation checks citation behavior. Passing those structural checks
doesn't by itself establish that all claims are supported or all required points are covered.

### An unjudged chunk makes precision unavailable

The `updated-content-001` case asks:

> How does documentation engineering connect the architecture and operations layers of a knowledge system?

The retrieval run returned 5 chunks: 4 counted as relevant and 1 as unjudged. It matched 4 of 5 primary sources,
so the case passed under the rule requiring at least one primary hit. Precision was `null` because one chunk was unjudged; recall was 0.571. This case explains
why the mean precision uses 13 of the 14 answerable cases.

Inspect its returned evidence and the dataset's judgments when comparing a run that changes precision
availability. A change in the mean can reflect a change in which cases have calculable precision.

## Compare with your own runs

1. **Check the benchmark inputs.** For a direct comparison, use the published version <code>{evaluationDatasetVersion}</code> dataset, the same
   corpus, and the same source judgments. Confirm that the indexed chunk IDs and content still correspond to
   those judgments. For another corpus, create expectations for its sources and identify the dataset separately.
2. **Record the run conditions.** Follow [Run the evaluation](/docs/evaluate/run-the-evaluation). Record the
   dataset version, indexed content, models, support cutoff, and requested chunk count so you can explain
   differences from the published snapshots.
3. **Compare counts as well as rates.** Check overall success, primary hits, recall, and how many cases contribute
   to mean precision. For expected-empty behavior, compare how many cases returned no chunks.
4. **Inspect individual cases.** Read failed cases and cases with unjudged results. Use the source text in the
   reports to understand a coverage failure or a change in precision availability.
5. **Review the saved answers separately.** Compare structural checks and human scores for the answer run under
   review. Human-review metadata must identify that saved answer run, and reviews must cover its required cases.

If the corpus or test cases differ, compare the evaluation approach and failure patterns. The percentages then
describe different benchmarks.

## Limitations

- **Corpus and sample:** The benchmark covers 22 cases on The Doc Landscape WordPress corpus. Its rates describe
  those cases and their recorded expectations.
- **Separate runs:** Retrieval and answer generation ran separately on October 22. Matching dataset versions and
  nearby timestamps don't establish that the indexed content was identical for both runs.
- **Incomplete coverage:** The `multi-section-001` retrieval case matched 1 of 3 primary sources and failed.
- **Precision availability:** Mean precision excludes `updated-content-001`. Its unjudged chunk requires attention when
  comparing precision across runs.
- **Review artifacts:** The approved local qualitative review isn't included in this snapshot. One reviewed answer
  run also doesn't measure consistency across repeated generation runs.
- **Replay inputs:** The snapshots preserve returned evidence and expectations. They don't include the full
  historical index or an implementation commit. The baseline reports also omit the reranking model and candidate
  depths, so they don't record every retrieval setting.

The Python RAG Service measures retrieval quality and answer quality with a versioned evaluation dataset. Each test
case pairs a query with the result the service should produce. Retrieval evaluation compares the chunks the retrieval
pipeline returns with that expected result. Answer evaluation checks the generated answer, including evidence
sufficiency and citations. A human review then scores support, completeness, and focus for answers from
answerable cases.

This page explains what that evaluation covers and why those checks stay separate.
[Retrieval evaluation](/docs/evaluate/retrieval-evaluation) defines the retrieval metrics.
[Answer evaluation](/docs/evaluate/answer-evaluation) defines the structural answer checks and the human review.
[Run the evaluation](/docs/evaluate/run-the-evaluation) is how to produce a new run.

## What the evaluation measures

- **Report metadata:** Each report records the dataset version, generation time, collection name, and selected model and retrieval settings.
- **Factors that affect results:** Changes to the embedding model, reranking model, chunking strategy, retrieval settings, or generation prompt can change evaluation results.
- **Test-suite checks:** The test suite loads the dataset and checks the scoring functions using fixture data.
- **Live evaluation:** The evaluation commands run live retrieval and answer generation outside the regular test suite and CI.

Run the evaluation again after a change that can affect retrieval or answer quality.

[Current evaluation results](/docs/evaluate/recorded-evaluation-results) records the latest completed run.

## The versioned evaluation dataset

The evaluation dataset is the maintained collection of test cases. The project stores it at `evaluation/datasets/baseline.json`.

The current dataset ID is `doc-landscape-baseline`, and the version is `1.5`. It's the human-labeled set for The Doc Landscape
WordPress index and contains 22 cases.

Reports and the human review record the dataset version they used. Both runs in a comparison need the same dataset version.

### Test-case fields

Each test case has a unique ID, a category, and a query. It can also include metadata filters and notes.

Every case in the current dataset filters retrieval to `source: wordpress` and includes both a retrieval expectation and
an answer expectation.

### Retrieval expectations

The retrieval expectation lists relevant sources, nonrelevant sources, and the expected-empty flag.

A **relevant source** is a chunk judged useful for the query. It records a document ID, a title, a heading path, and,
in this dataset, a chunk ID. Its role is:

- **`primary`:** Content the case treats as answer-bearing.
- **`supporting`:** Relevant content that doesn't have to carry the answer on its own.

When a relevant source omits `role`, the dataset treats it as primary. An answerable case includes at least one primary source.

A **nonrelevant source** is a chunk judged not useful for the query. It uses the same document, heading, and chunk fields.
Retrieval evaluation treats a returned chunk on neither list as **unjudged**.

### Answer expectations

The answer expectation records whether the case should have sufficient evidence.

When sufficient evidence is expected, the case also lists **required points**: ideas the qualitative review looks for in
the generated answer. The automated answer checks store these points with the result. The qualitative review assesses
whether the answer covers them.

### Dataset validation

Loading the dataset enforces these rules:

- Case IDs must be unique.
- An expected-empty case must have no relevant sources.
- A case that expects results must include at least one primary source.
- A source can't appear in both the relevant and nonrelevant lists.
- A chunk can't appear more than once within either list.

## Answerable and expected-empty cases

Each test case expects one of two retrieval outcomes: relevant chunks or no chunks.

### Expected outcomes

| Property | Answerable case | Expected-empty case |
| --- | --- | --- |
| Retrieval outcome | Relevant chunks. | No chunks. |
| `expect_empty` | `false` | `true` |
| Relevant sources | Includes at least one primary source. | Empty list. |
| Answer expectation in the current dataset | Sufficient evidence, with required points for review. | Insufficient evidence. |
| Number of cases in the current dataset | 14 | 8 |

Expected-empty cases use the category `unanswerable`. They can list nonrelevant sources for chunks close to the query's topic.

### How expected-empty cases test the support gate

**Expected-empty** is the expected result recorded in a test case. An **unsupported query** is a live question the indexed documentation can't adequately answer.

The support gate returns no chunks when:

- The highest rerank score is below the configured support cutoff.
- The reranker returns no chunks.

Expected-empty cases test whether this rule rejects questions the indexed documentation can't answer. See
[Retrieval pipeline](/docs/architecture/retrieval-pipeline) for how that decision works.

These cases cover two kinds of questions:

- **Questions unrelated to the indexed content:** For example, how long to roast a chicken.
- **Questions related to the topic but unanswered by the indexed content:** For example, choosing between Qdrant and
Pinecone or fine-tuning an embedding model.

Both kinds check that retrieval returns no chunks when the indexed content doesn't support the question.

### Test-case categories

Each category identifies the behavior the case tests.

| Category | Role in the current dataset |
| --- | --- |
| `exact_answer` | A question about a specific documented point. Includes 8 answerable cases. |
| `synonym` | A question that tests meaning-based retrieval. `synonym-001` asks how search recognizes differently worded questions. Its primary sources cover embeddings and semantic search. |
| `ambiguous` | A question open to more than one interpretation. `context-001` asks how important context is in documentation. |
| `confusable` | A question with a nearby subject that could be mistaken for the intended one. `documentation-engineering-001` asks what a documentation engineer does. `cms-selection-001` asks how to choose a content management system (CMS) for documentation. |
| `multi_section` | A question requiring more than one primary section. `multi-section-001` names three retrieval-failure mechanisms and lists a primary source for each. |
| `updated_content` | A question about revised documents in the current index. `updated-content-001` targets indexed content from a revised source document. |
| `unanswerable` | An expected-empty case where the indexed documentation doesn't contain an answer. |

## Retrieval evaluation and answer evaluation

Retrieval evaluation and answer evaluation use the same dataset but check different failures.

### Retrieval evaluation

Retrieval evaluation runs the production retrieval pipeline with each case's query, filters, and a result limit of 5. It compares the returned chunks with the expected result.

For answerable cases, it records primary-source coverage, precision, recall, and reciprocal rank.

| Case type | Passing condition |
| --- | --- |
| Answerable, other than `multi_section` | At least one primary source appears in the top five chunks. |
| `multi_section` | Every primary source appears in the top five chunks. |
| Expected-empty | The pipeline returns no chunks. |

### Answer evaluation

Answer evaluation runs the same retrieval step, then generates an answer from the retrieved chunks. Automated checks compare the evidence-sufficiency flag and citations with the case's expectations.

The reported flag must match `expected_sufficient_evidence`.

| Expected evidence sufficiency | Required citation behavior |
| --- | --- |
| Sufficient | At least one chunk is cited. Every cited chunk is a relevant source, and at least one is a primary source. |
| Insufficient | No citations are included. |

A structural pass requires both the evidence-sufficiency check and the citation check to pass.

### Citation validation and evaluation

Citation checks happen at two stages:

- **During answer generation:** Validation checks that citation IDs refer to sources supplied to the model and that inline
  citations match the declared IDs. The application takes citation titles, headings, and URLs from those source objects.
- **During evaluation:** Additional checks determine whether the cited chunks are relevant and primary sources according to the dataset.

### Why the evaluations stay separate

A retrieval gap and a weak answer are different failures. The returned chunks can miss part of the expected retrieval result
while still providing enough evidence for an answer.

In the recorded dataset `1.5` run, `multi-section-001` doesn't retrieve every primary section in the top five chunks. Its
generated answer nevertheless covers the required points. See [Known limitations](/docs/reference/known-limitations) for that
retrieval-coverage gap.

Successful retrieval and valid citations also don't establish that an answer stays focused on the question.

An earlier answer for `context-001` used the retrieved evidence but included related AI-assistant material. The question asked
about context in documentation. The grounded-answer prompt now instructs the model to ignore material that's related to the topic
but unnecessary for the question. That instruction guides generation; it doesn't determine exactly what the model will write.

## Automated checks and human review

Evaluation combines two kinds of checks:

- **Automated checks:** Score ranked chunks, evidence sufficiency, and citation behavior against the dataset.
- **Human review:** Assess whether an answer's claims are supported, its required points are covered, and its content
  stays focused on the question.

### Human-review dimensions

Reviewers score each answerable case from **0 to 2** on four dimensions:

| Dimension | What the reviewer checks |
| --- | --- |
| Support / faithfulness | Whether meaningful claims match the retrieved evidence. |
| Required-point completeness | Whether the answer covers the case's required points. |
| Unsupported details | Whether the answer adds claims the retrieved evidence doesn't support. |
| Focus / relevance | Whether the answer stays on the question. |

A strict pass requires a score of **2 on every dimension**.

### Review-file validation

The project stores review scores in `data/evaluation/answer_qualitative_review.json`. The file also records:

- Dataset ID.
- Dataset version.
- Answer-run time.
- Generation model.

The report command checks that these values match the answer run. It also checks that the reviewed cases match the cases
expecting sufficient evidence: the 14 answerable cases in the current dataset.

### Generated reports

Evaluation runs write JSON and Markdown reports under `data/evaluation/`.

These are local files. Git ignores `/data/`, so the reports aren't included in the repository.

See [Evaluation architecture](/docs/architecture/evaluation-architecture) for how the dataset, commands, and generated
files fit together.

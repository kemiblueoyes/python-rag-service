Use this quickstart when you want the shortest path from a fresh repo checkout to a successful `POST /v1/search` response.
It covers the minimum install, configuration, a reachable Qdrant server, WordPress indexing, startup, and authenticated search. Deeper options
for each step live on the related pages.

## Prerequisites

- Python 3.12 and [uv](https://docs.astral.sh/uv/)
- A Voyage AI API key for embeddings and reranking
- Docker, if Qdrant will run on this computer. Otherwise, a remote Qdrant URL and its API key
- A WordPress site whose REST API exposes the posts and pages you want to index

<Steps toc={true}>
    ## Install the project

    Clone the repository, then install dependencies from the project directory:

    ```bash
    git clone https://github.com/kemiblueoyes/python-rag-service.git
    cd python-rag-service
    uv sync --dev
    ```

    See [Install](/#) for the install requirements in more detail.

    ## Configure the local environment

    Copy the example environment file:

    ```bash
    cp .env.example .env
    ```

    Set these values in `.env`. Don't commit `.env` or put real keys in `.env.example`.

    ```dotenv
    RAG_API_KEY=your-long-random-api-key
    VOYAGE_API_KEY=your-voyage-api-key
    QDRANT_URL=http://localhost:6333
    QDRANT_API_KEY=
    QDRANT_COLLECTION=rag_chunks
    WORDPRESS_BASE_URL=https://example.com
    ```

    - `RAG_API_KEY` is the key clients send in the `X-API-Key` header.
    - `QDRANT_URL` and `QDRANT_API_KEY` in the example are for Qdrant on this computer.
      The next step starts that server, or replaces these two values for a remote instance.
    - `QDRANT_COLLECTION` defaults to `rag_chunks`. Change it if you want the service to
      use a different Qdrant collection name.
    - `WORDPRESS_BASE_URL` is the site the connector reads.

    The example file already sets the embedding model and WordPress collections to
    `posts` and `pages`.

    See [Configure the service](/#) for the rest of the environment variables, and
    [Authentication](/#) for how the API checks the key.

    ## Make Qdrant reachable

    Indexing stores embeddings in Qdrant, so make Qdrant reachable before the next command.

    <Tabs>
        <Tab title="Local">
            Start Qdrant with Docker in its own terminal and leave the container running.

            ```bash
            docker pull qdrant/qdrant
            ```

            The example `.env` matches this server: `QDRANT_URL` is `http://localhost:6333`
            and `QDRANT_API_KEY` is empty. A default local Qdrant doesn't check an API key.

            Run the following command from a directory outside the project.
            It creates a `qdrant_storage` folder there and keeps Qdrant's database files
            out of the repository.

            ```bash
            docker run -p 6333:6333 -p 6334:6334 \
                -v "$(pwd)/qdrant_storage:/qdrant/storage:z" \
                qdrant/qdrant
            ```

            This is Qdrant's recommended setup for local development. See 
            [Qdrant local quickstart](https://qdrant.tech/documentation/quickstart/).

        </Tab>
        <Tab title="Remote">
            Set your instance address and API key in `.env` before you index:

            ```dotenv
            QDRANT_URL=https://your-cluster.cloud.qdrant.io
            QDRANT_API_KEY=your-qdrant-api-key
            ```

            Qdrant Cloud requires an API key. A self-hosted remote instance requires one
            when API-key authentication is enabled on that server.

        </Tab>
    </Tabs>

    ## Index WordPress content

    To build the index before you search, run this command from the project directory. This
    command reads the configured WordPress site, writes canonical documents and chunks 
    under `data/`, and stores embeddings in Qdrant:

    ```bash
    uv run python -m rag_service.commands.index_wordpress --rebuild-vector-index
    ```

    When the command finishes, it prints how many canonical documents and chunks
    it wrote, and how many documents and chunks it stored in the vector index.

    See [Index WordPress content](/#) for incremental updates and what each artifact is for.

    ## Start the service
    
    Start the API from the project directory in its own terminal:

    ```bash
    uv run uvicorn rag_service.api.app:app --reload
    ```

    Open `http://127.0.0.1:8000/health`. A running service returns:

    ```json
    {
      "status": "ok"
    }
    ```

    The health check doesn't use the API key. `POST /v1/search` does.
 
    ## Send your first search request

    Call `POST /v1/search` with the key from `RAG_API_KEY`. Use a query that matches
    content you just indexed:

    ```bash
    curl -s -X POST http://127.0.0.1:8000/v1/search \
      -H "Content-Type: application/json" \
      -H "X-API-Key: your-long-random-api-key" \
      -d '{"query": "How does metadata improve retrieval?"}'
    ```

    ## Verification

    A successful search logs `200 OK` in the API terminal. The curl command prints a `results` array. 
    Each result includes the chunk title, heading path, excerpt, source URL, and rerank score. 
    
    The service can also return `200` with an empty `results` array when the indexed content doesn't
    support the query. If that happens, retry with a question your WordPress content
    actually covers.

    A missing or wrong `X-API-Key` returns `401`. If `RAG_API_KEY` isn't set, or Qdrant
    or Voyage can't be reached, search returns `503`.

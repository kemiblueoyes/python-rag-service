The Python RAG Service has constraints that affect what it can index, which evidence it retrieves, and how answers are generated
and checked. This reference describes those limitations, their practical effects, and available mitigations. Use it when deciding
whether the current implementation fits your content, integration, and quality requirements.

## Content sources and index freshness

### WordPress is the only implemented connector

The core pipeline uses a platform-neutral document model, but WordPress is the only implemented connector. Indexing another content
source requires a connector that maps its content into that model.

See [Indexing pipeline](/docs/architecture/indexing-pipeline) for the connector's role.

### Source changes require an indexing run

Publishing, updating, or unpublishing WordPress content doesn't automatically refresh the index. Retrieval and citations can reflect
older content until an indexing run completes.

Follow [Re-index and update content](/docs/index-content/re-index-and-update-content) after source changes.
Changes to embedding or chunking behavior require a full rebuild, as described in that procedure.

### Lexical refresh happens on the next request

After indexing replaces the configured `LEXICAL_CORPUS_PATH` file, each running API process checks file identity and metadata
on its next search or answer request. It builds a complete in-memory BM25 replacement before using it. Unchanged files reuse
the existing index. No API restart is required after indexing; changes to environment configuration still require a restart.

Refresh and lexical searches are serialized within each process. The request that triggers a refresh, and concurrent lexical
searches, wait for the build. A request already searching the previous snapshot can finish with that snapshot. No provider clients
are replaced or closed during refresh. Invalid, missing, unreadable, or continuously changing corpora return the existing controlled
configuration error instead of serving stale lexical results. A later request retries, allowing recovery after a valid publication.

Keep the public API and [operations runner](/docs/operations/run-operations-runner) as separate processes with access to the same corpus path. Every API worker refreshes
independently; there is no background watcher or cross-process notification. Publish complete files with atomic replacement, as the
WordPress indexer does. Qdrant updates and lexical publication aren't one transaction, so requests during indexing can still observe
different vector and lexical generations. File metadata checks avoid hashing the whole corpus on each request.

## Retrieval coverage and support detection

### Compound questions can miss primary sources

The retrieval pipeline ranks chunks by relevance without explicitly selecting evidence for each part of a compound question.

In the recorded `multi-section-001` case, the top five results were relevant but included only one of three designated primary sources.
The earlier answer passed human review, so the observed limitation concerns retrieval coverage.

For questions with several distinct parts, try separate queries and inspect their source coverage.
See [Recorded evaluation results](/docs/evaluate/recorded-evaluation-results) for the case details.

### The support cutoff needs validation for your corpus

The default `0.70` support cutoff was selected for the evaluated corpus and models. It isn't a universal boundary between supported
and unsupported queries.

The gate checks only the highest reranking score. An accepted query can still return chunks that don't support every part of the question.

Re-evaluate the cutoff when the corpus, models, chunking, or retrieval settings change.
See [Retrieval evaluation](/docs/evaluate/retrieval-evaluation) for the measurements and pass rules.

## Answer context and citation checks

### Answer context has a fixed retrieval depth and token budget

The answer endpoint retrieves up to five chunks. Clients can't increase that limit. Context assembly keeps whole chunks in rank order
and stops when the next serialized source array exceeds the token budget. The budget counts that JSON array, including escaping and
structure. It doesn't limit the question or the system message. This can leave useful evidence out of the model's context.

If the first chunk exceeds the budget, the request fails with `answer_unavailable`. Increasing the configured budget can address
that constraint, but doesn't increase retrieval depth.

See [Answer generation and citations](/docs/architecture/answer-generation-and-citations) for context selection and
[Configuration reference](/docs/reference/configuration-reference) for the budget setting.

### Valid citations don't establish factual support

Citation validation checks that citation identifiers match the supplied context. It doesn't judge whether the cited passages support
each claim, whether the answer is complete, or whether the model correctly reports sufficient evidence.

Use [Answer evaluation](/docs/evaluate/answer-evaluation) to assess support, completeness, unsupported details, and focus
through human review.

### Source text can still steer the model

The user message is JSON, so quotes, braces, and fake source boundaries in a question or chunk stay inside field values.
They don't add sources or fields to the parsed message. The service leaves documentation text intact, including passages that
contain instructions or code examples.

The model can still follow instructions that appear in those fields, such as a request to ignore the grounding rules. The service
doesn't run a separate check that detects or removes that text. A citation identifier that matches the supplied context still doesn't
show that the cited passage supports the claim.

## Service health checks

A successful `/health` response doesn't establish that search or answer is available. The endpoint doesn't check Qdrant, Voyage, OpenAI,
or the lexical corpus.

Use authenticated search and answer requests to check those workflows.
See [API reference](/reference/overview) for the endpoint references.

## Operations runner

### Only one runner job can be active

The runner accepts one active job and rejects another submission with HTTP 409 while
that job is queued or running. It doesn't keep a waiting queue. Run one process and
one worker without automatic reload. The runner locks its job database so another
runner can't use it at the same time. This requires a Unix-compatible operating system,
such as macOS or Linux. Keep the database on the computer running the runner.

This lock doesn't coordinate manual indexing or evaluation commands, or runners with
separate databases. Don't run those operations at the same time against the same index
and output files.

### Interrupted jobs aren't resumed or retried automatically

Jobs run inside the runner process. The database keeps job history, but it can't keep
a job running after the process stops. When you restart the runner, it marks unfinished
jobs as failed with `runner_interrupted`. The job may already have changed the index
or written files, and the runner doesn't undo those changes. Inspect the outcome
before submitting a new job with a fresh idempotency key.

The runner saves the lexical corpus before the document checkpoint, the saved document
snapshot used to detect changes. If saving the checkpoint fails, the new corpus can
remain alongside the previous checkpoint. The next indexing job still detects pending
changes. The runner updates Qdrant and the files separately.
See [Lexical refresh happens on the next request](#lexical-refresh-happens-on-the-next-request).

### Job requests can't override configuration

The operations API supports only incremental WordPress indexing and retrieval evaluation.
Requests can't select source URLs, datasets, paths, providers, or rebuild flags.
Configure the runner through its environment and restart it after configuration changes.
Use the command line for full rebuilds while no runner job is active.

### History and reports require storage management

The runner doesn't automatically delete job history or evaluation reports. Keep the
job database so you can look up past jobs and retry submissions with the same keys.
Deleting it also removes the record of previously used submission keys. Report paths
refer to files on the runner's computer. The operations API doesn't provide report downloads.

### Runner health and job success don't establish retrieval quality

The runner's health endpoint doesn't require authentication. It checks runner availability
and access to the job database. It doesn't check the operations key, providers, or lexical corpus.
An evaluation job can succeed even when test cases fail. Review the report and assess
quality separately. The runner doesn't apply a retrieval quality policy.

Follow [Run the operations runner](/docs/operations/run-operations-runner) for submission,
polling, error handling, and recovery procedures.

## n8n automation

### The included workflow evaluates only after content changes

The included n8n workflow skips evaluation when indexing finds no changes. A run
that skips evaluation doesn't establish current retrieval quality. If indexing
succeeds but evaluation or later handling fails, restarting the whole workflow
may skip evaluation because indexing already saved the updated checkpoint.
Run evaluation independently when needed. See
[Recover when evaluation is skipped or later handling fails](/docs/operations/set-up-n8n-workflow#recover-when-evaluation-is-skipped-or-later-handling-fails).

### Workflow timeouts don't necessarily cancel runner jobs

The exported workflows have a configurable ten-minute timeout. Stopping an n8n
execution doesn't necessarily cancel a Python job it already submitted. Check the
existing job's status and result before retrying to avoid unnecessary replacement
work. See [Configure settings for both workflows](/docs/operations/set-up-n8n-workflow#configure-settings-for-both-workflows).

### The comparator supports schema 1 and policy version 1

The included comparator supports only schema version 1 and policy version 1.
Unsupported versions stop the workflow with an error instead of producing a
quality pass. Use compatible policy and baseline files. Supporting another format
or policy version requires updating the workflow's validation and comparison code.
See [Prepare and verify your policy and baseline](/docs/operations/set-up-n8n-workflow#prepare-and-verify-your-policy-and-baseline).

## Evaluation scope

The recorded benchmark covers 22 cases on The Doc Landscape corpus. Its results don't establish quality for other corpora or query patterns.

Retrieval and answer evaluation were recorded in separate runs. The snapshots don't establish that both used identical indexed content.
Human review covers one set of 14 answers and doesn't measure consistency across repeated generation runs.

Evaluate your own corpus and representative queries before relying on the recorded rates.
See [Recorded evaluation results](/docs/evaluate/recorded-evaluation-results) for run conditions and comparison limits,
and [Run the evaluation](/docs/evaluate/run-the-evaluation) to generate your own reports.

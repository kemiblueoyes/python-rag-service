The API reference documents the public HTTP API of the Python RAG Service. Clients call `POST /v1/search`,
`POST /v1/answer`, and `GET /health`. Indexing runs through the `index_wordpress` command. See
[Index WordPress content](/docs/index-content/index-wordpress-content).

The route pages in this reference are generated from the service OpenAPI description. A running
service also serves that description at `/openapi.json` on the service origin.

For how search and answer differ, and for which of those two routes to call, see
[Search and answer](/docs/search-and-answer/overview).

## Key capabilities

The reference covers three routes.

| Endpoint | Purpose |
| --- | --- |
| [Search indexed docs](api:POST/reference/search): `POST /v1/search` | Retrieve ranked documentation passages with source links. |
| [Generate grounded answer](api:POST/reference/answer): `POST /v1/answer` | Generate an answer from retrieved evidence and return supporting sources. |
| [Health check](api:GET/reference/health): `GET /health` | Check whether the service process responds to requests. |

Each endpoint reference describes its request, response, and documented status codes.

`POST /v1/search` retrieves documentation chunks. `POST /v1/answer` generates a grounded answer.
`GET /health` reports whether the service process is responding. Each link opens that route's
request, response, and status codes.

## Authentication

Search and answer requests require an `X-API-Key` header whose value matches the service's `RAG_API_KEY`.
Send this key from your application back-end. `GET /health` doesn't require authentication.

See [Authentication](/docs/get-started/authentication) for setup and request examples.

## Versioning

Search and answer are served under the `/v1` prefix. `GET /health` is served at `/health`. In the
OpenAPI description, `info.version` is `0.1.0`.

## Request and response conventions

`POST /v1/search` and `POST /v1/answer` accept a JSON body and return JSON. Send
`Content-Type: application/json`. A completed call returns HTTP 200.

HTTP 200 can also contain an empty search result or an answer with `sufficient_evidence` set to false.
These are completed requests, not API errors.

Both request schemas require `query`. The service trims leading and trailing whitespace, then
accepts 1 to 2,000 characters. It measures that length in Unicode code points. Each filter value
accepts 1 to 256 characters after trimming, and a filter list accepts 1 to 50 values. Search
`limit` accepts an integer from 1 to 20. The default is 5. Both schemas reject fields they don't
define. A body larger than 65,536 bytes (64 KiB) returns HTTP 413 with `request_too_large` before
JSON parsing. See [Errors](/reference/errors). These limits don't restrict request rate, and they
don't cap provider spending.

`GET /health` takes no request body and returns `{"status": "ok"}` when the service process responds.
It doesn't check retrieval, answer generation, or connections to Qdrant, Voyage, or OpenAI.

## Error responses

Documented authentication, validation, and availability errors use a shared JSON structure containing an `error`
object with `code`, `message`, and `details`.

Use `code` to identify the error. Validation errors also include details about invalid request fields. See
[Errors](/reference/errors) for the response format, status codes, and error codes.

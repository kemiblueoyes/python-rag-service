The included WordPress client lets site visitors search indexed documentation and ask for a grounded
answer through the Python RAG Service. The browser sends Search and Ask requests to WordPress. The
plugin calls the Python RAG service from PHP and keeps the service URL and API key on the server.

The WordPress connector indexes source content. This page covers the WordPress client, which calls
the public API and renders Search and Ask for visitors. Index that content before you expect Search
or Ask to return documentation. See
[Index WordPress content](/docs/index-content/index-wordpress-content).

The plugin doesn't add a settings screen in wp-admin. You set the service URL and API key in
`wp-config.php`, add the `[python_rag_service]` shortcode, and deploy the plugin directory.
Optional constants set how many Search and Ask requests the site forwards each minute.

## Prerequisites

- **[Authentication](/docs/get-started/authentication)**: Set `RAG_API_KEY` on the Python RAG service.
  The WordPress API key constant has to use that same value.
- **[Index WordPress content](/docs/index-content/index-wordpress-content)**: Build the index that
  Search and Ask retrieve.

## Install the reference client

Copy the complete `clients/wordpress/python-rag-service-client/` directory from this repository into
the WordPress `wp-content/plugins/` directory. Keep the directory name. The plugin's main file
should be:

```text
wp-content/plugins/python-rag-service-client/python-rag-service-client.php
```

That directory includes `includes/` and `assets/`. The main file loads the proxy classes from
`includes/`, and the shortcode loads `assets/rag-search.js` and `assets/rag-search.css`.

In wp-admin, activate **Python RAG Service Client**. Activation registers the
`[python_rag_service]` shortcode and the REST routes `python-rag-service/v1/search` and
`python-rag-service/v1/answer`.

## Set the service URL and API key

Define the Python service origin and API key in `wp-config.php` before the `/* That's all, stop editing! Happy publishing. */` comment:

```php
define(
    'RAG_SERVICE_API_BASE_URL',
    'https://your-rag-service.example.com'
);

define(
    'RAG_SERVICE_API_KEY',
    'replace-with-the-same-long-random-value'
);
```

`RAG_SERVICE_API_BASE_URL` is the service origin only. The plugin removes a trailing slash, then
appends `/v1/search` or `/v1/answer`. Leave those paths out of the constant. Point the constant
at the API itself. The plugin doesn't follow a redirect, and it keeps certificate verification
on. An origin that only redirects to the API fails the call. See
**Route Search and Ask through WordPress** for that failure.

`RAG_SERVICE_API_KEY` has to match `RAG_API_KEY` exactly. The plugin sends that value in the
`X-API-Key` header. See [Authentication](/docs/get-started/authentication) for how the Python RAG
service checks the header, and [Configuration reference](/docs/reference/configuration-reference)
for both WordPress constants.

WordPress calls `RAG_SERVICE_API_BASE_URL` from the server that runs PHP. The visitor's browser
doesn't call that URL. During local development, the Python RAG service has to be running at an
address the WordPress server can reach. When WordPress is hosted on another machine,
`http://127.0.0.1:8000` on your computer isn't that address. A temporary HTTPS tunnel can connect
them. For a deployed site, set `RAG_SERVICE_API_BASE_URL` to the origin of the hosted Python RAG
service.

If either constant is undefined, Search and Ask return HTTP 500 with the message
`The RAG service URL isn't configured.` The plugin returns that same message when only
`RAG_SERVICE_API_KEY` is undefined.

## Choose how many requests to forward

Search and Ask stay available without a WordPress login. The plugin limits how many of those
requests it forwards to Python. The default is 30 Search forwards and 10 Ask forwards per minute.
Every visitor shares the Search allowance, and every visitor shares the Ask allowance. The plugin
ignores `X-Forwarded-For`, `CF-Connecting-IP`, and other visitor-supplied forwarding headers, so
those headers don't create a separate allowance.

Set either limit in `wp-config.php` when you want a different positive integer:

```php
define( 'RAG_SERVICE_SEARCH_REQUESTS_PER_MINUTE', 30 );
define( 'RAG_SERVICE_ANSWER_REQUESTS_PER_MINUTE', 10 );
```

Leave a constant undefined to keep its default. The value has to be an unquoted integer of 1 or
greater. Zero, a negative number, a decimal, or a quoted string is invalid. An invalid Search
value stops Search from calling Python and returns HTTP 503 with
`Search is temporarily unavailable.` Ask keeps its own limit. An invalid Ask value stops Ask the
same way and leaves Search unchanged.

The counters live in the WordPress database, in `{prefix}rag_service_rate_limits`. On a site whose
table prefix is `wp_`, that table is `wp_rag_service_rate_limits`. Each route has one row. The
stored minute only moves forward. A reservation that still names an earlier minute is rejected,
including after the same route moves its row forward and after the other route runs cleanup. That
reservation doesn't open a counter for the earlier minute.

The plugin creates the table with `dbDelta` when you activate the plugin. If the plugin is already
active when you copy these files in, the next request replaces the table when the
`rag_service_rate_limit_schema` option isn't `2`. Replacing the table clears the counts already
stored. No Redis server or other new service is required. Admission uses the stored count, so a
connection that reports an unchanged row as a match still rejects a full minute. The plugin
doesn't change that connection's flags. Concurrent PHP workers share the same counter.

The window is a fixed minute. A new minute starts the counter at one. Traffic at the end of one
minute and the start of the next can use both allowances, so a short period can reach twice the
limit. The limit counts an attempt after the plugin reserves a slot, including an attempt that
Python then fails. Empty and overlong queries are rejected before a slot is reserved.

This limit protects the volume of Search and Ask requests the WordPress proxy sends. It doesn't
apply to another client that calls the Python RAG service directly. It isn't a spending cap for
Voyage or OpenAI, and it isn't a complete denial-of-service defense. The site still accepts the
HTTP request, and other public WordPress routes are unchanged.

## Add the shortcode

Add the shortcode to the page or post where visitors should search:

```text
[python_rag_service]
```

The client displays a query field with Search and Ask buttons. Both buttons are disabled while a request runs.

Search displays matching passages with document titles, heading paths, and short excerpts. Titles link to the source documents.
When a heading anchor is available, the deepest heading links directly to that passage. If no results are returned, the client displays
`No relevant results found.`

Ask displays the answer with basic formatting for paragraphs, bulleted lists, and bold text. Citations link to supporting sources,
and a `Sources` list appears when the response includes sources.

When `sufficient_evidence` is false, the client also displays `The available pages and articles may not contain enough information.`

</Steps>

Visitors can then run Search and Ask on the published page. Their browsers call the WordPress
routes. The plugin adds the API key when it calls the Python RAG service.

## Route Search and Ask through WordPress

The shortcode posts the visitor's query to WordPress. The browser request doesn't include the API
key, a result limit, or metadata filters.

Search sends a JSON body with `query` to `python-rag-service/v1/search`. The plugin then calls
`POST /v1/search` on `RAG_SERVICE_API_BASE_URL` with that query, `limit` set to 5, and
`X-API-Key`. The WordPress HTTP request times out after 15 seconds.

Ask sends the same kind of body to `python-rag-service/v1/answer`. The plugin calls
`POST /v1/answer` with `query` only. That route doesn't accept `limit`.

On a site that uses the default WordPress REST prefix, the browser calls:

```text
https://your-wordpress-site.example/wp-json/python-rag-service/v1/search
https://your-wordpress-site.example/wp-json/python-rag-service/v1/answer
```

A successful proxy call returns the Python response body with HTTP 200. See
[Search documentation](/docs/search-and-answer/search-documentation) and
[Generate grounded answers](/docs/search-and-answer/generate-grounded-answers) for those fields.

The form doesn't submit an empty query. After `sanitize_text_field` and trimming, the REST routes
reject an empty query before they reserve a rate-limit slot or call Python. Search returns HTTP 400
with `A search query is required.` Ask returns HTTP 400 with `A question is required.`

A query longer than 2,000 Unicode code points returns HTTP 422 with `The query is too long.` The
plugin counts code points, not bytes. `é` counts as one code point. A one-code-point
emoji counts as one. A combining mark counts as its own code point, so `e` followed by a combining
acute accent counts as two. The message doesn't include the query. The Python service still applies its
own query, filter, and body-size checks. See [Errors](/reference/errors).

When the shared counter for a route is full, that route returns HTTP 429 with
`Too many requests. Try again shortly.` and a `Retry-After` header. The header is the number of
seconds left in the current minute. The Search and Ask script shows the REST `message` and enables
the buttons again. It doesn't send the rejected request again.

Python HTTP 413 becomes HTTP 413 with `The request is too large.` Python HTTP 422 becomes HTTP 422
with `The request couldn't be processed.` Those visitor messages are fixed. They don't include the
Python error body, the query, the API key, or exception text.

Connection failures, timeouts, a wrong API key, a missing or invalid limit setting, a rate-limit
storage failure, a redirect, a non-JSON body, and provider failures stay on HTTP 503. Search uses
`Search is temporarily unavailable.` Ask uses `Answer generation is temporarily unavailable.` The
plugin doesn't call Python when storage fails or the limit setting is invalid.

<Note>
WordPress doesn't require a logged-in user for `python-rag-service/v1/search` or
`python-rag-service/v1/answer`. A client that can reach the site can send Search and Ask through
the proxy. Those routes share the site-wide limits in **Choose how many requests to forward**.
The API key stays in `wp-config.php`.
</Note>

## Source links

The browser accepts an absolute `http` or `https` URL with a host and no username or password.
Uppercase and lowercase scheme names are both accepted. It rejects other schemes, including
`javascript:` and `data:`, along with malformed URLs, relative URLs, URLs that contain whitespace,
and URLs that embed credentials.

A rejected URL stays on the page as the title, heading, citation, or source name. That text isn't a
link. One rejected URL doesn't stop the other results or the rest of the answer from rendering.
Titles, excerpts, headings, and answer text stay text. Links that open a new tab keep
`rel="noopener noreferrer"`.

The browser applies this check to results already stored in the index, including a URL that was
indexed before this check existed. Indexing applies the same rule when WordPress records are
ingested again. A published record with body text whose source URL fails the check is saved as a
canonical document and produces no chunks. The indexing log includes the WordPress record ID and
doesn't include the URL. Deploying the updated browser script doesn't require you to delete or
rebuild the live index. Ingest the documents again when you want the indexing check to apply to
records fetched on that run.

## Deploy plugin updates

After you change the reference client, copy the complete
`clients/wordpress/python-rag-service-client` directory to `wp-content/plugins` again. Updating
the Python RAG service on its own doesn't update the live WordPress proxy or the Search and Ask
interface.

On a site where the plugin is already active:

1. Copy the plugin directory over `wp-content/plugins/python-rag-service-client`. Leave the plugin
   active. You don't have to deactivate it.
2. Load any page, or call either REST route. The plugin replaces `{prefix}rag_service_rate_limits`
   when `rag_service_rate_limit_schema` isn't `2`. Replacing the table clears the counts already
   stored. If that table can't be created, Search and Ask return HTTP 503 and the plugin doesn't
   call Python.
3. Add `RAG_SERVICE_SEARCH_REQUESTS_PER_MINUTE` or `RAG_SERVICE_ANSWER_REQUESTS_PER_MINUTE` in
   `wp-config.php` only when you want a limit other than 30 or 10.
4. Confirm `RAG_SERVICE_API_BASE_URL` is the API origin. The updated plugin doesn't follow a
   redirect from that origin.
5. Reload the page that contains `[python_rag_service]` so the browser loads the updated
   `assets/rag-search.js`. The plugin versions that file from its modification time. You don't
   have to delete or rebuild the live index for the browser source-link check.

When the service origin or API key changes, update `RAG_SERVICE_API_BASE_URL` or
`RAG_SERVICE_API_KEY` in `wp-config.php`. The plugin reads those constants on each request. It
doesn't store them as WordPress options. The request limits are constants too. The schema flag is
the one option this plugin writes.

This plugin is a reference client for `POST /v1/search` and `POST /v1/answer`. Change the plugin
and deploy that directory when you need different proxy or interface behavior. Other applications
can call the same public API. See
[Integrate the RAG API into an application](/docs/integrate/integrate-rag-api-into-application).

## Verification

Open the published page that contains `[python_rag_service]` and check both actions:

1. Confirm that the query field and Search and Ask buttons appear.
2. Run Search with a query your indexed content supports. Confirm that results appear and their source links
open the expected documents or passages.
3. Run Ask with a question your indexed content supports. Confirm that the answer appears and any citation and
source links open the expected supporting content.

You can also call the WordPress proxy without an API key. The plugin adds `X-API-Key` on the
server. On a site that uses the default REST prefix:

```bash
curl -s -X POST https://your-wordpress-site.example/wp-json/python-rag-service/v1/search \
  -H "Content-Type: application/json" \
  -d '{"query": "How does metadata improve retrieval?"}' \
  | python -m json.tool
```

A working proxy returns HTTP 200 and the `POST /v1/search` body. Missing constants return HTTP 500
and `The RAG service URL isn't configured.` A key that doesn't match `RAG_API_KEY`, a service URL
that WordPress can't reach, or an origin that redirects, returns HTTP 503 and
`Search is temporarily unavailable.` An empty query returns HTTP 400. A query of more than 2,000
Unicode code points returns HTTP 422 and `The query is too long.` More than 30 forwarded Search
requests in the current minute returns HTTP 429, `Too many requests. Try again shortly.`, and
`Retry-After`.

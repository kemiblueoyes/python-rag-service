Use the included WordPress client to let visitors search indexed documentation and request answers grounded in that content.

The visitor's browser sends Search and Ask requests to WordPress. The plugin calls the Python RAG Service from PHP,
keeping the service URL and API key on the server.

The **WordPress client** displays results and answers. The **WordPress connector** indexes the content they use.
Before using the client, [index your WordPress content](/docs/index-content/index-wordpress-content).

This guide covers installing the plugin, configuring the connection and request limits, and adding the `[python_rag_service]`
shortcode. Configuration lives in `wp-config.php`; the plugin doesn't provide a settings page in wp-admin.

## Prerequisites

- **[Authentication](/docs/get-started/authentication)**: Set `RAG_API_KEY` on the Python RAG service.
  The WordPress API key constant has to use that same value.
- **[Index WordPress content](/docs/index-content/index-wordpress-content)**: Build the index that
  Search and Ask retrieve.

## Install the reference client

Copy the complete `clients/wordpress/python-rag-service-client/` directory from this repository into
the WordPress `wp-content/plugins/` directory. Keep the directory name. The plugin's main file
should be:

```text
wp-content/plugins/python-rag-service-client/python-rag-service-client.php
```

That directory includes `includes/` and `assets/`. The main file loads the proxy classes from
`includes/`, and the shortcode loads `assets/rag-search.js` and `assets/rag-search.css`.

In wp-admin, activate **Python RAG Service Client**. Activation registers the
`[python_rag_service]` shortcode and the REST routes `python-rag-service/v1/search` and
`python-rag-service/v1/answer`.

## Set the service URL and API key

Add these constants to `wp-config.php` before the `/* That's all, stop editing! Happy publishing. */` comment:

```php
define(
    'RAG_SERVICE_API_BASE_URL',
    'https://your-rag-service.example.com'
);

define(
    'RAG_SERVICE_API_KEY',
    'replace-with-the-same-long-random-value'
);
```

| Constant | What to set |
| --- | --- |
| `RAG_SERVICE_API_BASE_URL` | The Python RAG Service origin, such as `https://your-rag-service.example.com`. Don't include `/v1/search` or `/v1/answer`. |
| `RAG_SERVICE_API_KEY` | The exact value of the service's `RAG_API_KEY`. The plugin sends it in the `X-API-Key` header. |

### Choose an address WordPress can reach

The server running WordPress and PHP calls the service URL. The visitor's browser doesn't call it.

- **Local development:** The Python RAG Service must be running at an address the WordPress server can reach.
If WordPress runs on another machine, it can't reach your computer's service through `http://127.0.0.1:8000`.
A temporary HTTPS tunnel can connect them.
- **Deployed site:** Use the origin of your hosted Python RAG Service.

### URL requirements

- Point the URL directly at the API. The plugin doesn't follow redirects.
- Leave out the endpoint paths. The plugin removes a trailing slash and appends `/v1/search` or `/v1/answer`.
- HTTPS certificate verification remains enabled.

An origin that redirects to the API fails the call. See **Route Search and Ask through WordPress** for how the plugin handles that failure.

### Missing configuration

If either constant is undefined, Search and Ask return HTTP 500 with:

```text
The RAG service URL isn't configured.
```

The plugin returns this same message even when only `RAG_SERVICE_API_KEY` is undefined.

See [Authentication](/docs/get-started/authentication) for API-key validation and
[Configuration reference](/docs/reference/configuration-reference) for both constants.

## Choose how many requests to forward

Search and Ask are available without a WordPress login. The plugin limits how many requests it forwards to the Python RAG Service.

Each action has a separate allowance shared by all visitors:

| Action | Default allowance |
| --- | --- |
| Search | 30 forwarded requests per minute. |
| Ask | 10 forwarded requests per minute. |

These are site-wide limits, not per-visitor limits. The plugin ignores forwarding headers such as `X-Forwarded-For` and
`CF-Connecting-IP`; they don't create separate allowances.

### Change the limits

To change either default, define its constant in `wp-config.php`:

```php
define( 'RAG_SERVICE_SEARCH_REQUESTS_PER_MINUTE', 30 );
define( 'RAG_SERVICE_ANSWER_REQUESTS_PER_MINUTE', 10 );
```

Leave a constant undefined to keep its default.

Values must be **unquoted integers of 1 or greater**. Zero, negative numbers, decimals, and quoted strings are invalid.

| Invalid setting | Effect |
| --- | --- |
| Search limit | Search returns HTTP 503 with `Search is temporarily unavailable.` and doesn't call Python. Ask remains available under its own limit. |
| Ask limit | Ask returns HTTP 503 with `Answer generation is temporarily unavailable.` and doesn't call Python. Search remains available under its own limit. |

### How requests are counted

- **Fixed-minute windows:** Each new minute starts a fresh counter. Requests near the end of one minute and the start of
  the next can use both allowances, allowing up to twice the limit within a short period.
- **Failed attempts count:** Once the plugin reserves a slot, the attempt counts even if the Python request fails.
- **Invalid queries don't count:** Empty queries and queries longer than 2,000 Unicode code points are rejected before a slot is reserved.
- **Full allowances reject requests:** The route returns HTTP 429 with `Too many requests. Try again shortly.` A `Retry-After`
  header gives the seconds remaining in the current minute.

### Counter storage

Counters are stored in the WordPress database in `{prefix}rag_service_rate_limits`. With the default `wp_` prefix, the table
is `wp_rag_service_rate_limits`.

Search and Ask each have one counter row. Concurrent PHP workers share these counters; no Redis server or additional service
is required.

The stored minute only moves forward. A reservation for an earlier minute is rejected, even after counter updates or cleanup.
It can't reopen an earlier window or bypass a full allowance.

The plugin creates the table during activation. If you update an already-active plugin, the next request replaces the table
when `rag_service_rate_limit_schema` isn't `2`. Replacing the table clears the existing counts.

### Scope of the limits

These limits control requests forwarded by the WordPress proxy. They:

- Don't apply to clients that call the Python RAG Service directly.
- Don't cap Voyage or OpenAI spending.
- Don't provide complete protection against denial-of-service attacks.

WordPress still receives the incoming HTTP requests. Other public WordPress routes are unaffected.

## Add the shortcode

Add the shortcode to the page or post where visitors should search:

```text
[python_rag_service]
```

The client displays a query field with Search and Ask buttons. Both buttons are disabled while a request runs.

Search displays matching passages with document titles, heading paths, and short excerpts. Titles link to the source documents.
When a heading anchor is available, the deepest heading links directly to that passage. If no results are returned, the client displays
`No relevant results found.`

Ask displays the answer with basic formatting for paragraphs, bulleted lists, and bold text. Citations link to supporting sources,
and a `Sources` list appears when the response includes sources.

When `sufficient_evidence` is false, the client also displays `The available pages and articles may
not contain enough information.`

</Steps>

Visitors can then run Search and Ask on the published page. Their browsers call the WordPress
routes. The plugin adds the API key when it calls the Python RAG service.

## Route Search and Ask through WordPress

The shortcode sends the visitor's query to WordPress. The browser request contains `query` only—no API key,
result limit, or metadata filters.

The plugin adds `X-API-Key` when it calls the Python RAG Service.

### Request routes

| Action | WordPress REST route | Python endpoint | Forwarded body |
| --- | --- | --- | --- |
| Search | `python-rag-service/v1/search` | `POST /v1/search` | `query` and `limit: 5`. |
| Ask | `python-rag-service/v1/answer` | `POST /v1/answer` | `query` only. The endpoint doesn't accept `limit`. |

Both Python requests use `RAG_SERVICE_API_BASE_URL`. The WordPress HTTP request for Search times out after 15 seconds.

With the default WordPress REST prefix, the browser calls:

```text
https://your-wordpress-site.example/wp-json/python-rag-service/v1/search
https://your-wordpress-site.example/wp-json/python-rag-service/v1/answer
```

A successful proxy call returns HTTP 200 with the Python response body. See [Search documentation](/docs/search-and-answer/search-documentation) and [Generate grounded answers](/docs/search-and-answer/generate-grounded-answers) for the response fields.

### Query validation

The form doesn't submit an empty query. The REST routes also apply `sanitize_text_field`, trim the query, and check its
length before reserving a rate-limit slot or calling Python.

| Invalid query | Status | Message |
| --- | --- | --- |
| Empty Search query | 400 | `A search query is required.` |
| Empty Ask query | 400 | `A question is required.` |
| More than 2,000 Unicode code points | 422 | `The query is too long.` |

Length is measured in Unicode code points, not bytes. A single-code-point `é` or emoji counts as one. An `e` followed by a
separate combining acute accent counts as two.

The message doesn't include the query. The Python service also applies its own query, filter, and body-size checks.
See [Errors](/reference/errors).

### Rate-limit responses

When an action's shared allowance is full, WordPress returns:

- **Status:** HTTP 429.
- **Message:** `Too many requests. Try again shortly.`
- **`Retry-After`:** The number of seconds remaining in the current minute.

The interface displays the message and enables the buttons again. It doesn't automatically retry the rejected request.

### Service and proxy failures

| Failure | Status returned by WordPress | Visitor message |
| --- | --- | --- |
| Python returns HTTP 413 | 413 | `The request is too large.` |
| Python returns HTTP 422 | 422 | `The request couldn't be processed.` |
| Search encounters another service or proxy failure | 503 | `Search is temporarily unavailable.` |
| Ask encounters another service or proxy failure | 503 | `Answer generation is temporarily unavailable.` |

HTTP 503 covers:

- Connection failures, timeouts, incorrect API keys, redirects, non-JSON responses, and provider failures.
- Missing or invalid request-limit settings and rate-limit storage failures.

The plugin doesn't call Python when the limit setting is invalid or rate-limit storage fails.

Visitor messages are fixed. They don't expose the Python error body, query, API key, or exception text.

<Note>
The WordPress routes don't require a logged-in user. Any client that can reach the site can send Search and Ask
requests through the proxy, subject to the site-wide limits in **Choose how many requests to forward**. The
API key stays in `wp-config.php`.
</Note>

## Source links

The client checks source URLs before displaying them as links.

### Accepted URLs

A source URL must:

- Be an absolute `http` or `https` URL with a host.
- Contain no username or password.
- Contain no whitespace.
- Be correctly formed.

Scheme names can use uppercase or lowercase letters.

The client rejects relative URLs and other schemes, including `javascript:` and `data:`.

### Rejected URLs

When a URL fails validation, its title, heading, citation, or source name still appears as text, without a link. Other
results and the rest of the answer continue to display.

Titles, excerpts, headings, and answer content remain text. Links that open a new tab use `rel="noopener noreferrer"`.

### Existing and newly indexed content

URL validation applies at two stages:

| Stage | Behavior |
| --- | --- |
| Browser display | Checks URLs in all returned results, including content indexed before this validation existed. |
| WordPress indexing | Applies the same URL rules to records fetched during that indexing run. |

During indexing, a published record with body text and an invalid source URL is saved as a canonical document but
produces no chunks. The indexing log includes the WordPress record ID, without the URL.

Deploying the updated browser script doesn't require deleting or rebuilding the live index. Ingest documents again
when you want the indexing check to apply to those records.

## Deploy plugin updates

After you change the reference client, copy the complete
`clients/wordpress/python-rag-service-client` directory to `wp-content/plugins` again. Updating
the Python RAG service on its own doesn't update the live WordPress proxy or the Search and Ask
interface.

On a site where the plugin is already active:

1. Copy the plugin directory over `wp-content/plugins/python-rag-service-client`. Leave the plugin
   active. You don't have to deactivate it.
2. Load any page, or call either REST route. The plugin replaces `{prefix}rag_service_rate_limits`
   when `rag_service_rate_limit_schema` isn't `2`. Replacing the table clears the counts already
   stored. If that table can't be created, Search and Ask return HTTP 503 and the plugin doesn't
   call Python.
3. Add `RAG_SERVICE_SEARCH_REQUESTS_PER_MINUTE` or `RAG_SERVICE_ANSWER_REQUESTS_PER_MINUTE` in
   `wp-config.php` only when you want a limit other than 30 or 10.
4. Confirm `RAG_SERVICE_API_BASE_URL` is the API origin. The updated plugin doesn't follow a
   redirect from that origin.
5. Reload the page that contains `[python_rag_service]` so the browser loads the updated
   `assets/rag-search.js`. The plugin versions that file from its modification time. You don't
   have to delete or rebuild the live index for the browser source-link check.

When the service origin or API key changes, update `RAG_SERVICE_API_BASE_URL` or
`RAG_SERVICE_API_KEY` in `wp-config.php`. The plugin reads those constants on each request. It
doesn't store them as WordPress options. The request limits are constants too. The schema flag is
the one option this plugin writes.

This plugin is a reference client for `POST /v1/search` and `POST /v1/answer`. Change the plugin
and deploy that directory when you need different proxy or interface behavior. Other applications
can call the same public API. See
[Integrate the RAG API into an application](/docs/integrate/integrate-rag-api-into-application).

## Verification

Open the published page that contains `[python_rag_service]` and check both actions:

1. Confirm that the query field and Search and Ask buttons appear.
2. Run Search with a query your indexed content supports. Confirm that results appear and their source links
open the expected documents or passages.
3. Run Ask with a question your indexed content supports. Confirm that the answer appears and any citation and
source links open the expected supporting content.

You can also call the WordPress proxy without an API key. The plugin adds `X-API-Key` on the
server. On a site that uses the default REST prefix:

```bash
curl -s -X POST https://your-wordpress-site.example/wp-json/python-rag-service/v1/search \
  -H "Content-Type: application/json" \
  -d '{"query": "How does metadata improve retrieval?"}' \
  | python3 -m json.tool
```

A working proxy returns HTTP 200 and the `POST /v1/search` body. Missing constants return HTTP 500
and `The RAG service URL isn't configured.` A key that doesn't match `RAG_API_KEY`, a service URL
that WordPress can't reach, or an origin that redirects, returns HTTP 503 and
`Search is temporarily unavailable.`

An empty query returns HTTP 400. A query of more than 2,000 Unicode code points returns HTTP 422 and
`The query is too long.` More than 30 forwarded Search requests in the current minute returns HTTP 429,
`Too many requests. Try again shortly.`, and `Retry-After`.

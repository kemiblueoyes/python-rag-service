Call `POST /v1/search` and `POST /v1/answer` from your application back end. The visitor's browser sends a query to your application.
Your back end adds the API key, calls the Python RAG Service, and returns the response data to the browser. The browser displays the
results or answer.

Search and answer both retrieve the current index. An answer request also uses the service's language-model configuration. See
[Generate grounded answers](/docs/search-and-answer/generate-grounded-answers).

## Prerequisites

- **Running service:** The Python RAG service must be running at an address your application server can reach.
  See [Quickstart](/docs/get-started/quickstart).
- **[Authentication](/docs/get-started/authentication):** Configure `RAG_API_KEY` on the service and set the same value
  in your application server's environment.
- **[Index WordPress content](/docs/index-content/index-wordpress-content):** Build the index that search and answer requests retrieve.
- **Answer generation:** Configure the language-model provider if your application uses `POST /v1/answer`.
  See [Generate grounded answers](/docs/search-and-answer/generate-grounded-answers).

## Keep the API key on the application server

Store the API key in your application server's environment. Its value must match the Python RAG Service's `RAG_API_KEY`.

For each search or answer request:

1. The visitor's browser sends the query to your application back end.
2. Your back end reads the API key from its environment.
3. Your back end calls the Python RAG Service with the key in the `X-API-Key` header.

<Warning>
Don't include the key in browser JavaScript or in any response returned to the visitor.
</Warning>

See [Authentication](/docs/get-started/authentication) for how the service checks the header.

The WordPress client follows this pattern: the browser calls WordPress, and WordPress adds the key when calling the service.
See [Integrate with WordPress](/docs/integrate/integrate-with-wordpress).

## Forward the user's query

Create a back-end route that accepts the visitor's query and calls the Python RAG Service. Use the `call_rag` helper below
to choose the endpoint:

| Application action | Helper call |
| --- | --- |
| Search | `call_rag("/v1/search", query)` |
| Request an answer | `call_rag("/v1/answer", query)` |

Return the HTTP status and response body through your framework's response API so the browser can display the result.

### Request setup and limits

Replace `http://127.0.0.1:8000` in the example with an address your application server can reach. Keep `/v1/search` and `/v1/answer`
in the individual helper calls.

Both endpoints require a JSON body containing `query`.

| Field or constraint | Requirement |
| --- | --- |
| `query` | 1–2,000 characters after trimming leading and trailing whitespace. Length is measured in Unicode code points. |
| Search `limit` | An integer from 1–20. Default: `5`. The answer endpoint rejects this field. |
| Request body size | Maximum 65,536 bytes (64 KiB). Larger bodies return HTTP 413. |

See [Search documentation](/docs/search-and-answer/search-documentation) for filters and `limit`, and [Errors](/reference/errors)
for validation failures. These limits don't restrict request rate or cap provider spending.

### Set the client timeout

Set a timeout for the request from your application server to the RAG service.

- The example uses **60 seconds for blocking network operations**.
- Answer requests also wait for the language model. Choose a timeout that accommodates the response times you observe.
- Coordinate this timeout with any timeout on your application server or hosting platform.

This client timeout is separate from the service's provider timeouts. Provider timeouts apply to individual calls, not
the whole search or answer request. See [Timeouts and retries](/docs/reference/timeouts-and-retries).

### Add the request helper

```python
import json
import os
from urllib.error import HTTPError
from urllib.request import Request, urlopen

# Replace with an address your application server can reach
SERVICE_ORIGIN = "http://127.0.0.1:8000"

def call_rag(path, query, timeout=60):
    request = Request(
        f"{SERVICE_ORIGIN}{path}",
        data=json.dumps({"query": query}).encode(),
        headers={
            "Content-Type": "application/json",
            "X-API-Key": os.environ["RAG_API_KEY"],
        },
        method="POST",
    )

    try:
        with urlopen(request, timeout=timeout) as response:
            payload = json.loads(response.read().decode())
            return response.status, payload
    except HTTPError as error:
        payload = json.loads(error.read().decode())
        return error.code, payload
```

The helper returns `(status, payload)` for successful requests and documented API errors. If `RAG_API_KEY` is missing,
`os.environ["RAG_API_KEY"]` raises `KeyError` before sending the request.

### Handle the response

Check `status` before reading response fields:

- **HTTP 200:** Read the search or answer fields.
- **Documented API error:** Read `payload["error"]`.

Handle these additional failures in your application route:

| Exception | What it means |
| --- | --- |
| `URLError` | The request failed, for example because the service couldn't be reached. |
| `TimeoutError` | A network operation timed out. |
| `json.JSONDecodeError` | The response wasn't valid JSON. |

For these failures, return a short unavailable message to the browser. Don't assume an API error body is available.

## Show search results

Call `call_rag("/v1/search", query)`, then check that `status` is `200` before reading the result fields.

`payload["results"]` contains the retrieved chunks in reranked order. For each result, display:

| Field | How to display it |
| --- | --- |
| `title` | The source document's title. |
| `heading_path` | The heading hierarchy, provided as a list of strings. Omit it when the list is empty. |
| `excerpt` | The retrieved passage. |

### Link to the source passage

Build each result's source link from `url` and `anchor`:

- `url` identifies the source document.
- `anchor` identifies the heading within that document. It's `null` when the chunk has no anchor.

Use this helper to build the link:

```python
def source_link(result):
    url = result["url"]
    anchor = result.get("anchor")
    if anchor:
        return f"{url.split('#', 1)[0]}#{anchor}"
    return url
```

When an anchor is present, the link opens the document at that heading. Otherwise, it opens the document URL.

### Handle empty results

An empty `results` list means no relevant results were returned. Show a message such as “No relevant results found.”

The status is still HTTP 200. Treat this as a completed search, not an API error.

See [Search documentation](/docs/search-and-answer/search-documentation) for the support gate, filters, and other result fields.

## Show the answer

Call `call_rag("/v1/answer", query)`, then check that `status` is `200` before reading the response fields.

The response includes `answer`, `sources`, and `sufficient_evidence`. Use `sufficient_evidence` to decide what to display:

| Value | What to display |
| --- | --- |
| `true` | Show `answer` with links to the cited sources. |
| `false` | Show `answer` on its own. `sources` is empty. |

An insufficient-evidence response still returns HTTP 200. Display the returned `answer` text; its wording can vary.

### Link citations to sources

A citation marker such as `[S1]` in `answer` matches the `citation_id` of an entry in `sources`.

- Match each marker to its source using `citation_id`.
- Build the source link with the `source_link` helper from [Show search results](#show-search-results).
- Display sources in their returned order, which follows the first appearance of each citation marker in `answer`.

`citation_id` applies only to the current response. Use `chunk_id` and `document_id` when you need identifiers to store.

### Citation validation

The service validates citations against the retrieved chunks before returning the answer. A failed citation check
returns `answer_unavailable`.

See [Generate grounded answers](/docs/search-and-answer/generate-grounded-answers) for response fields and citation validation.

## Present API errors

For a documented API error, `call_rag` returns the HTTP status and a JSON error body. For example, a
missing or incorrect API key returns:

### Choose how the application responds

Read `payload["error"]["code"]` to identify the error and choose the appropriate response:

| Status | Error | Application behavior |
| --- | --- | --- |
| 401 | `authentication_failed` | Check the API key configured on your application server. |
| 413 | `request_too_large` | Reduce the request body size. |
| 422 | `validation_error` | Use `error.details` to identify and correct invalid request fields. |
| 503 | `authentication_unavailable`, `retrieval_unavailable`, or `answer_unavailable` | Show an unavailable state. |
| 500 | `configuration_error` | Show a generic failure message. The service settings need correction. |
| 500 | `internal_error` | Show a generic failure message. The service encountered an unexpected error. |

### Check server diagnostics

For handled HTTP 500 and 503 failures, the Python RAG Service logs the failed operation and a diagnostic reason.

- **Local development:** Check the terminal where you started Uvicorn.
- **Hosted deployment:** Check your hosting platform's application logs.

The diagnostic reason isn't included in the API response. `LOG_LEVEL` controls these `rag_service` log lines.

See [Errors](/reference/errors) for status codes, error codes, messages, and validation details.

search results or an empty-result state. It shows the answer with source links, or the answer
alone when `sufficient_evidence` is false.

## Verification

### Check successful responses

From your application server, call the `call_rag` helper from **Forward the user's query** and print the status and response body:

```python
import json

status, payload = call_rag(
    "/v1/search",
    "How does metadata improve retrieval?",
)
print(status)
print(json.dumps(payload, indent=2))
```

Repeat the check with `/v1/answer` in place of `/v1/search`.

| Endpoint | Expected status | Response fields |
| --- | --- | --- |
| `/v1/search` | `200` | `query` and `results`. |
| `/v1/answer` | `200` | `answer`, `sources`, and `sufficient_evidence`. |

### Check browser behavior

In the browser's network panel, confirm that:

- Queries go to your application back end.
- The API key is absent from browser requests and responses.

### Check error and empty states

| Test | Expected behavior |
| --- | --- |
| Send a request from your application server with an incorrect API key. | The service returns HTTP 401 with `authentication_failed`. Your application displays an error state. |
| Test a search that returns an empty `results` list. | The service returns HTTP 200. Your application displays a no-results state. |
| Test an answer with `sufficient_evidence: false`. | The service returns HTTP 200 with an empty `sources` list. Your application displays the answer without source links. |
